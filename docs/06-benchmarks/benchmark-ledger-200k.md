# 200K 口径基准数据台账

> 用途：多组参数实验数据汇总，找 K 深度 / KV 类型 / 上下文长度的平衡点。
> 口径铁律：本表所有数据必须同口径（冷 prompt 唯一 nonce / C1 / greedy temp0 / 输出 384）才可横向比较。
> 板：p3960-0010 Jetson AGX Thor T5000，DriveOS 7.0.3，CUDA 12.8.90 驱动，60GB 统一内存
> 模型：QUASAR-NVFP4-text.gguf（19.65G，生产同款）+ Qwen3.8-27B-MTP-Q4_K_M.gguf（16.8G，09-09 起）+ williamliao Quality-v2（16.06G，NVFP4）

**09-09 晚会战结论（A4/Radix 路线排查）**：
1. **NVFP4 原生 kernel 在 sm_101a 数值错误**（"1+1="→乱码实锤；A4-1/A4-2 双重验证）。上游只在 sm_120（RTX 50 系）验证过；Thor T264/14SM 无人验证。修复=等上游或自己改 kernel（远期）
2. **llama.cpp master（5d806aa）qwen35 内置 MTP 全链路在 Thor 跑通**（A4-3/A4-4：正确性✅、接受率✅），但 decode 5.94 vs 老栈 12.32——**验证 batch（8 tok/步 forward）开销 > 投机收益**，老 build 外挂 MTP（轻验证链）依旧最优
3. **Q4_K_M 在新 build 20K 口径 prefill 235.9 t/s**（老 build 同口径 135-158），但 200K 长上下文优势消失（140.7）——新 kernel 的长上下文 attention 路径无优化
4. **williamliao Quality-v2（16.06GB）SHA256=6007d4b0...25cb 已存板**：/brand_data/ai_workspace/models/（NVFP4 kernel 修复后可复用）
5. **Radix 34.91 三壁垒定案**：私有 FP8 kernel（100% 带宽效率）+ NVFP4 小权重 + 深度 MTP 验证链优化——全部在其私有 runtime，llama.cpp 参数层面不可追

**2×2 矩阵结论（09-09，真 200K 口径）**：
- **最优 = K7 + f16（12.32 t/s）**；最差 = K12 + q8_0（7.60），极差 62%
- **f16 全面碾压 q8_0**：200K 长尾下 q8_0 反量化开销 + 草稿质量劣化（接受率 0.763→0.597）双重惩罚
- **K7 优于 K12**（f16 下 -9%，q8_0 下 -14%）：深 MTP 链在长上下文反而拖累
- 与社区 25.89 差距 2.1×，参数已对齐（K7+f16）仍差一半 → 差距不在 K/KV 参数，转向大页/llama.cpp 版本/CUDA Graph 覆盖率排查（R5 大页实验）

**⚠️ 09-09 首轮 R2-R4 数据作废**（11:35-11:44 跑的）：bench 脚本校准 token 密度时读写了死的 R1 日志（194925 tokens），算出错误密度 194.9/unit（正常 ~12），prompt 实际只有 ~12K tokens 而非 195K。作废数据（12K 上下文口径，仅作短上下文参考）：R2 K12+f16=14.03 / R3 K7+q8_0=16.71 / R4 K12+q8_0=15.07 t/s。已修：日志路径参数化 + 密度范围校验（5-25/unit，超范围中止）。

**⚠️ 09-09 二轮 R2-R4 空跑作废**（11:47-11:53，5 分钟全失败）：修复时加的"校准前 truncate server 日志"引入新 bug——server 进程持有日志文件句柄，truncate 后它从旧偏移继续写，文件变成 NUL 稀疏文件，grep 判定为二进制不匹配 → 校准读不到 token 数 → 三组连锁失败。教训：**不要 truncate 被进程持有的日志文件**；per-tag 日志每组由 server 启动时 `>` 重定向新建，本就无跨组污染，truncate 是多余的。已修：去掉 truncate，保留密度范围校验。

**R1 关键结论（09-09）**：25.89 社区配方（K7+f16）在我们板上实测 **12.32 t/s，仅社区值 48%**。MTP 本身工作正常（接受率 0.763），差距来源待 R2-R4 扫描定位（K 深度 / KV 类型 / 社区口径细节）。

**参考锚点（非本表口径，仅供对照）**：
- 社区网友 25.89 t/s：QUASAR + MTP K7 + FP16 KV + 195,686 冷 prompt + C1 + Prefix OFF + 输出 384（用户 09-09 提供）
- 官方教程 35 t/s：Jetson 线（JetPack 7 / CUDA 13 驱动）+ Q4_K_M + MTP，**DRIVE 线不可比**（D10）
- 短 prompt 生产口径：15.32 / 10.51 t/s（predictable / creative，K12 + q8_0 + 64K ctx）

## 四、平衡点分析（数据齐后填）

- K 深度：**K7 优于 K12**（f16 下 12.32 vs 11.19 = -9%；q8_0 下 8.88 vs 7.60 = -14%）。短 prompt 实验的 K12 结论在 200K 反转
- KV 类型：**f16 全面优于 q8_0**（-28~-14%）。q8_0 双重惩罚：①decode 每 token 全量遍历 KV 时反量化开销被 195K 长尾放大；②KV 精度损失导致 MTP 草稿质量劣化（接受率 0.763→0.597）。64K 生产场景省显存的好处，在 200K 场景被速度损失碾压
- **生产选型（200K 场景）**：K7 + f16 KV + c 200704。若显存吃紧（f16 200K KV ≈ 19.2GB + 权重 19.65G + 激活 ≈ 45GB/61.5GB），可考虑 c 降到 131072（128K，KV ≈ 12.6GB）
- ⚠️ **结果不理想声明（2026-09-09）**：当前最优 12.32 t/s 距社区 25.89 还差 2.1×，参数维度（K/KV/ctx）已排除。**差距必在更底层**，待查假设按优先级：
  1. **大页（hugetlbfs）**：板上 43GB hugetlb 池（21504×2MiB）完全闲置，llama-server HugetlbPages=0；网友板"40GiB AI Pool 20480×2MiB free=0"疑为进程真用大页 → 2MiB 页 TLB 压力降 512×，decode 全量遍历 195K KV 时收益可能巨大（R5 实验已备好：`scripts/bench200k-hugepage.sh`，模型 mmap 进 /dev/hugepages）
  2. **llama.cpp 版本**：我们 5d806aa vs 官方 Thor 栈 b10373（2026-08-12），官方栈的 attention/MTP kernel 可能有针对 Thor 的优化没进 master
  3. **CUDA Graph 覆盖率**：decode 是否每 token 真走 graph（server 日志 graphs reused 计数偏低，13 次/384 tok，需对照官方栈）
  4. 社区口径残差：网友可能用 llama-bench 直测（无 API 层开销）或非流式口径
- **板已含关机计划**：用户 2026-09-09 13:4x 决定关机整理电源和冷却（矩阵跑完 GPU tj 81°C、prefill 尾部 128 t/s 减速疑与热相关但未实锤节流），开机后从"大页实验 R5"继续
- **09-09 晚路线更新**：R5 大页实验被 Radix A4 路线排查插入（E1/E2/A4 系列见上表）；**"大页+老栈 12.32"与"新栈内置 MTP"两条路的对照数据已齐**，老栈胜出。R5 大页实验仍待跑（对老栈做，可能仍有收益）

## 四、带宽天花板定案（09-11 R26-R28 系列，A1-DECISION 文档）

- **128K decode 62ms/token ≈ KV 读取 16.5GB ÷ 273GB/s = 60ms + 权重 19.6GB 的 MTP 摊薄**——KV 读取带宽受限实锤

- **16.4±0.7 t/s @128K 是本板+本模型实用天花板**；突破需架构级（GQA/MLA 减 KV 读取量）
