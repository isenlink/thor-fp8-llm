# 长上下文精度自检清单（8 方向）

**为什么必须自测**：速度读数随接受率浮动，看起来"更快"的配置可能悄悄换了输出。

**我们自己的读数（2026-09-19，150 题 × 8 方向，temp=0、预算 512）**：

- **chat 接口（`/v1/chat/completions`，= 生产前端用法）：32K 与 200K 都是 150/150 全对、0 空回答。**
- raw-completion（自己拼 `doc + "\nAnswer:"` 走 `/completion`）：200K 会出现**空回答 37/150（24.7%）**，
  且**去掉起草器后逐题一致** ⇒ 是**题面形态 + 长上下文**的效果，与二进制/起草器无关；**换 chat 接口即消失**。
  该形态下已给出答案的题 112/113 = 99.1% 正确。
- 换配置会改答案：去掉起草器会翻掉 1 题（letter 计数）⇒ 精度口径要绑定配置。

## 口径（不做这几条，测出来的数字没意义）

- `temperature=0`、`seed` 固定、`n_predict ≥ 512`（预算太小会把"没答完"误判成"答错"；我们踩过：预算 48–160 时 69/150 的答案被截断在 `<think>` 里）
- **用 chat 接口**（`/v1/chat/completions`）；自己拼 raw prompt 时注意长上下文会触发空回答
- **同一套题在 32K 和 200K 各跑一遍**，两边都要过
- **空回答（content 为空）一律判错**，不要从 reasoning/`<think>` 里捞答案
- 判分机器化（正则/JSON 解析），不要人眼扫一遍就说过

## 8 方向 · 每题给标准答案

### 1. 算术运算
```
17*23=?            -> 391
(48+56)*7=?        -> 728
1024-357=?         -> 667
```
### 2. JSON 格式跟随
```
只输出 JSON，不要任何解释：{"name":"thor","scores":[1,2,3],"ok":true}
只输出 JSON 数组，3 个元素，每个是 {"i":<序号从1开始>,"sq":<序号的平方>}
```
判据：能被 `json.loads` 直接解析；键名/类型/顺序一致；**多一个字都算错**。
### 3. 列表计数约束
```
列出 5 项，每项不超过 8 个字，最后一行单独写"共5项"。
```
判据：项数 == 5；每项 ≤8 字；最后一行严格等于 `共5项`。
### 4. 标识符转录
```
把 THR-9f3K-77qZ-0042 原样输出三次，每次一行。
```
判据：逐字符比对（大小写敏感），三行完全相同。
### 5. 字母计数
```
strawberry 中字母 r 出现几次？  -> 3
mississippi 中字母 s 出现几次？ -> 4
bookkeeper 中字母 o 出现几次？  -> 2
```
判据：只认最终数字；写推理链但答案错 = 错（我们有 2 题就是这样退化的）。
### 6. 数字排序
```
把 [42, 7, 19, 3, 88, 15] 升序排列，只输出结果 -> 3, 7, 15, 19, 42, 88
输出这份列表里的第 4 大值 -> 15
```
### 7. 数字串转录
```
把 860314735209 逐位输出，用空格分隔 -> 8 6 0 3 1 4 7 3 5 2 0 9
把 860314735209 倒序输出，用空格分隔
```
判据：位数、顺序、分隔符全对。
### 8. 中英混排转录
```
原样输出，中英标点都保留：Thor 板卡 NVFP4 量化后 decode 22.18 t/s（见 §3）。
```
判据：中英文与半/全角标点逐字符一致（这是最容易在长上下文里被"顺手改写"的项）。

## 判定

- 32K：全对才算合格；出现空回答也算失败（我们实测 150/150）。
- 200K：用 chat 接口应全对（我们实测 150/150）；raw 题面下的空回答见上文归因。
- 非空回答里的正确率：**≥98%**（我们自己的读数：chat 形态两档均 100%；raw 形态非空 112/113 = 99.1%）。
- 想更强：把 24 题扩到 150 题（每方向 15–20 题），跑 3 个 pass，看**波动**而不只看均值。
