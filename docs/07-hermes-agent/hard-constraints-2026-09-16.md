# Hard constraints that look like a broken install (and the anti-patterns behind them)

**中文标题：看起来像"装坏了"的硬约束，以及背后的反例**

> 日期：2026-09-16 · 平台见 `README.md`

## 0. 适用范围（先读这条）

**第 1、2 条仅在"以板本机 `llama-server` 作为 Agent 后端"时适用**。
若后端是云端 API（如外网 DeepSeek），本机不跑服务，就不会遇到这两条——
不要把它们当成所有部署的通用前提。第 3、4、5 条与后端选择无关，通用。

## 1. Agent 要求模型上下文窗口 ≥64K（仅本地后端）

**现象**：`hermes chat` 直接拒绝初始化：

```
Failed to initialize agent: Model <name> has a context window of 16,384 tokens,
which is below the minimum 64,000 required by Hermes Agent. ...
```

**原因**：Agent 侧有最小窗口门槛（提示里也给了另一条路：若服务端报的窗口小于模型真实窗口，
可在配置里显式声明模型真实窗口，仍须 ≥64K）。

**处理**：把本地模型的上下文开够。本平台实证：该模型 KV 仅 **64 KB/token**（65 层中只有 16 层全注意力），
`-c 262144` 时 KV = 16.8 GB，加权重与草稿共 **35.0 GB < 46 GB 大页池** ⇒ 直接开原生上限即可。
**上下文上限设大不会拖慢短输入**（解码只看实际 KV 长度），所以不要为了"省"而开小。

## 2. 本地 llama-server 必须带 `--cache-ram 512`（仅本地后端）

**现象**：连续换新提示词提问，进程内存线性增长，**约第 12 个不同提示词后被 OOM 杀**；
重复同一提示词则完全平坦（说明不是"泄漏"，而是"每个新提示词都会新增一份主机侧缓存"）。

**根因**：服务端默认 `--cache-ram 8192`（MiB）的上限**大于本机常规可用内存**
（大页池占掉后常规侧只剩数个 GB）⇒ 缓存还没涨到自己的天花板，进程先被杀。

**剂量-反应证据**（只改一个参数，各跑 15 个不同提示词）：

| `--cache-ram` | 请求 3 | 6 | 9 | 12 | 15 | 表现 |
|---|---:|---:|---:|---:|---:|---|
| `0` | 2044 | 2047 | 2054 | 2054 | **2054** | 涨 +689 MB 后平坦 ✅ |
| `512` | 2515 | 2518 | 2525 | 2525 | **2525** | 涨 +1157 MB 后平坦 ✅ |
| 默认 8192 | 3137 | 5004 | 6875 | 8691 | ❌ OOM | 线性增长，第 13 个请求连接被断 |

**处理**：固定 `--cache-ram 512`——封顶内存且**保留前缀缓存**（"一次载入、反复提问"的用法不受影响）。
验证：30 个不同提示词、单实例一轮跑完，内存封顶后完全平坦。

## 3. 只读根上放不了 shim（`/usr/local/bin` 不可写）

**现象**：`ln -sf <wrapper> /usr/local/bin/<name>` 看起来"执行成功"，实际什么都没发生——若命令尾部带
`|| true`，失败会被**静默吞掉**，直到某天在登录 shell 里发现命令找不到。

**实测**：
```bash
$ touch /usr/local/bin/.wtest        # Read-only file system
$ sudo touch /usr/local/bin/.wtest2  # Read-only file system（加 sudo 一样）
```

**处理**：用 `/etc/profile.d/99-<name>.sh` 导出 `PATH`/`HERMES_HOME`（overlay 可写，由恢复脚本重建），
wrapper 本体放持久分区。**并且：恢复脚本里的每一步都要在复验段里能被验证**——
不要用 `|| true` 掩盖"本该成功的动作"。

## 4. 出厂解析器指向平台预置的遗留地址 ⇒ 一切域名解析挂死

**现象（最容易被误判成"网络慢/模型慢"）**：Agent 首轮问答耗时数分钟，日志：

```
Stream stale for 180s (threshold 180s) — no chunks received. model=...
Streaming failed before delivery: Request timed out.
Retrying API call in 2.1s … <成功>
```
一次实测：**3 min 11 s**（重试后 1 s 成功）。同一现象在另一台板表现为**6/6 域名全部无应答**。

**根因**：出厂 `/etc/resolv.conf` 指向**平台预置的遗留解析器地址**，该地址落在**车载内网 VLAN 的路由上**，
而默认路由在**另一个网口**上 ⇒ 不是"解析慢"，而是**根本到不了**。
（另一台板逐服务器实测：该解析器对 **6/6 个域名全部超时**，其余 3 个公共解析器全部正常。
同一现象在两台板的表现不同——一台是"请求静默 180 s 后超时"，一台是"6/6 域名无应答"，
因为是否有其它解析器可回落、以及应用层的超时策略不同。）

**正确取证姿势（三步，缺一不可）**：
1. **裸 API 延迟**（绕开 Agent，直接用脚本打一次请求）——判断端到端到底是"模型慢"还是"链路慢"；
2. **按 IP 直连**（排除 DNS）：能连上 ⇒ 出网没问题，问题在解析；
3. **逐解析器探测**（网关 / 公共解析器 / 那个遗留地址）——实测：网关与公共解析器都有应答，
   **只有遗留地址全超时**。

**处理**：解析器**跟随默认路由**（网关 + 一个公共解析器），并加 `options timeout:2 attempts:2` 防挂死；
母本放持久分区，**由恢复脚本在 overlay 被吞后写回**。
**反例**：不要长期靠 `/etc/hosts` 手工条目录绕过——只覆盖已知域名，新域名仍挂死，且掩盖了真实故障。

**效果**：同一台板，修 DNS 前 3 min 11 s → 修后 **2–3 s**（裸 API 0.43–0.81 s）。

## 5. 兜底能力本身要有存活证明

真实事故（另一台板）：宿主侧守护的日志目录放在 tmpfs，宿主重启后守护进入 auto-restart 死循环，
**兜底能力静默归零 8 h 49 min**——没有告警，也没有日志。任何"看护/兜底"设计都要能回答：
它现在活着吗？怎么证明？失效时谁会知道？
