## 2. Thor 硬件事实（ccprobe 实测 + ptxas 探针）

- 14 SMs、CC 10.1（sm_101a）、47GB 统一内存、L2 24MB、带宽 ~230-246 GB/s
- dp4a ≈32/SM/clk（1/4 率）→ wide-M dp4a 路线上限 ~103 GB/s（实测 97 到顶）
- **无 FP4/int8-k64 张量核**：mma kind::mxf4nvf4 与 s8 m16n8k64 均被 ptxas 拒绝；
  llama.cpp 对 Thor 走 Ampere 配置（256 线程/occ=1/I=128/LAYOUT_NVFP4/K_vram=256）
  + NVFP4→q8 解码 + int8 m16n8k32 MMA
- verify NVFP4 实测 2.57 T MAC/s ≈ int8-MMA 理论（5.4T）的 48%（cuBLASLt FP8 对照 55%）
  → **verify 是算力-bound，不是带宽-bound**

## 4. 核心机制认知（128K 每步账本）

step ≈ 287ms = verify 地板 132ms（KV 16.5GB 全读 60ms + 权重 72ms，均已到顶）
+ draft 链 ~85ms（7.7 次前向 × 8.73ms）+ 采样等 ~10ms；acceptance 5.66 tok/step。
**128K 下 acceptance 是主导乘数：draft 侧任何带宽节省都买不回 acceptance 损失。**
现实上限 ≈（132 + 最小 draft 40ms）÷ 5.66 ≈ 33 t/s，且要求 draft 减半且 acc 无损。
→ 30 t/s 目标在 L0/L1 工程手段内无候选；需模型侧（更好的 MTP 头/更深 draft）。

## 5. 三次 GPU 通道死锁事故与现行纪律（详见 INCIDENTS-gpu-channel-deadlock.md）

- 9/12 13:07、9/13 11:28、9/13 14:56 三次，签名一致（error notifier 13 → irq/296 D 态
  → ~25 分钟恶化 → 只能物理断电 ≥10s）。全部由 **kernel 级代码改动**触发
  （两次对齐 fault、一次 MMQ config 组合 hang），与负载大小/温度无关。
- **现行实验分级**：L0 host 侧/参数/模型文件走既有路径 = 正常流程；L1 复用已验证算子
  的新图组合 = 2K 先行；**L2 新 kernel/kernel 源码/MMQ config = 条件放行**
  （用户特批框架：串口监测在线 + 逐次特批 + 静态审查 + 一次一变量 +
  小负载 canary + 现场可断电时段，详见 INCIDENTS 文档）。
- 操作规程：跑 GPU 前 协作邮局 值守方线程预告；先 2K 后 128K；一次一个变量；
  *.BADHANG 管理打挂产物；notifier 出现即停手等断电。
- 板卡恢复后纪律：**先五项洁净检查**（uptime/残留进程/内核日志/大页池+文件/冒烟），
  通过并回报后才允许实验。
