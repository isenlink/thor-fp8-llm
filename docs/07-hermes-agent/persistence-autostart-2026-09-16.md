# Surviving dirty power loss: where the assets live and how the agent comes back

**中文标题：脏断电存活 —— 资产放哪、恢复什么、两种自启挂点及各自代价**

> 日期：2026-09-16 · 平台见 `README.md`

## 一、板子的现实（决定了整个架构）

| 位置 | 掉电后的命运 |
|---|---|
| `/`（只读根） | hypervisor 层写保护：`mount -o remount,rw`、`dd`、`debugfs` 等全部无效 |
| `/etc`、`/home`、`/media` | **overlay 上层，fsck 判错后被格式化** |
| `/brand_data/`（独立持久分区） | 多次脏断电实测存活 |

⇒ **结论**：能持久的东西只有数据分区；**板内也没有任何可插入的自启钩子**（启动链全在只读根上）。
因此自启必须"**板外常电主机 → 串口登录 → 跑恢复脚本**"，恢复脚本负责把 overlay 侧的薄壳重建出来。

## 二、分工：什么放持久区、什么放 overlay

**持久区（母本，永不丢）**
- `venv/`、`HERMES_HOME`（config、`.env`、skills、state.db、sessions、logs）
- systemd 单元**母本**、启动 wrapper、`env.sh`、恢复脚本、离线包目录/文档

**overlay（薄壳，每次恢复重建）**
- `/etc/systemd/system/hermes.service`、`/etc/systemd/system/llama-server.service`（或同类本地模型服务）
- `/etc/profile.d/99-hermes.sh`（环境变量；**只读根上 `/usr/local/bin` 不可写**，不能用 shim 符号链接）
- `/etc/resolv.conf` 与解析器 drop-in
- 大页池 sysctl 配置（本平台 CUDA 分配路径依赖固定大页池，掉电后回落到出厂值）

## 三、恢复脚本（幂等）该做什么

顺序建议（缺一项都可能表现为"服务起不来")：

1. 目录与属主兜底（持久区 + `chown` 到 `user`）
2. 启动 wrapper 与 `env.sh`（写回持久区）
3. **重装 systemd 单元**：从持久区母本 `cmp` 比对，有差异才 `install`（幂等）
4. **环境变量**：重建 `/etc/profile.d/99-hermes.sh`
5. **大页池兜底**：低于目标值才设置（多次设置无害，但别无条件覆写）
6. **DNS 修正**：见 `hard-constraints-*.md` 第 4 条（**必须每次重建**，否则解析挂死）
7. 时间同步兜底（overlay 恢复后 `sudoers`/时区可能未就绪，服务依赖正确时钟）
8. `daemon-reload` → `enable` → 先起本地模型服务、后起 Agent → **复验**（服务状态、DNS、模型端可达、端到端）
9. `sync` 落盘

## 四、两种自启挂点（两台板各用一种，可并存）

### 挂点 A：板端恢复脚本钩子（board3 采用）
在板端既有的 `restore_overlay.sh` **末尾追加钩子**，调用 Agent 自己的恢复脚本。

- 优点：只改一处、一跳完成；恢复动作与其它板端恢复项（账号/网络/大页池）在同一事务里，顺序可控。
- **落地必须满足三条硬要求**（两台板共识）：
  1. **fail-open**：母本缺失或数据分区未挂载时静默跳过；任何一步失败都不得中断主恢复流程。
     ⚠️ 注意主恢复脚本**带 `set -e`**，所以钩子必须保证**所有分支都返回 0**
     （`bash 恢复脚本 || echo "…已跳过"` **且** 补 `else` 分支），否则"跳过"会被当成"恢复失败"。
  2. **幂等**：只做"母本 → overlay 拷贝 + `daemon-reload`"，重复执行不产生重复项（用内容比对决定是否安装）。
  3. **它改的是出厂件**：该恢复脚本 `root` 所有、出厂自带（本平台实测为 5 月版本）。
     **刷板或他人接手后钩子会丢** ⇒ 板外常电主机的兜底调用是**必需品，不是可选项**（见挂点 B）。
- 代价：**该文件是 root 所有且在多块板上共用**（改动前必须备份原文件；钩子必须幂等、可只加一次、
  失败不阻塞主流程：`bash restore-agent.sh || echo "[agent] 恢复脚本返回非零"`）。
- 注意：该文件自身也在持久分区上，所以钩子不会丢。

### 挂点 B：宿主侧守护的恢复命令表（board4 采用）
不碰板端共用文件，把恢复调用挂到**宿主侧守护**（串口看护进程）的 `RESTORE_CMDS` 里，紧跟其原有板端恢复之后。

- 优点：不改板端共用件；板端恢复项与 Agent 恢复项由同一宿主侧编排，便于统一审计。
- 代价：**多一跳，且守护自身必须先活着**。真实事故（board4，2026-09-16）：守护日志目录放在 tmpfs，
  宿主重启后三个守护进入 auto-restart 死循环，**兜底能力静默归零 8 h 49 min**（无告警、无日志）。
  ⚠️ **归因要分清：这是"实现缺陷"（日志落 tmpfs），不是"宿主侧触发路线"的固有缺陷**——
  把实现缺陷写成路线风险会误导读者。正确读法：任何承载兜底职责的进程，都必须自带存活证明
  （日志落持久盘 + 外部可见的心跳/探针 + 失败显式告警）。
- **必要性**：由于挂点 A 改的是出厂件、刷板即丢，宿主侧兜底在工程上是**必需品**；两条并存才是完整方案。

### 推荐
**挂点 A 为主 + 挂点 B 兜底**：板端一跳完成、不依赖守护；宿主侧再加一条探测——若发现板端钩子缺失
（例如换板/刷板后未恢复），就直接调 Agent 恢复脚本。两者都写进文档，代价如上。

## 五、不等真断电的等价验收

见 `verification-2026-09-16.md`。核心思想：**手动制造"overlay 被吞"的等价状态**（删单元、删 profile、改坏 DNS、停服务），
再跑恢复脚本，逐项复验。不必真的清空 overlay——真清空会让板子同时失联（静态 IP 也丢），现场成本远高于收益。

## 六、兜底设计的两条通用教训

1. **兜底能力本身要有存活证明**：守护不能只报"我跑过了"，还要能被外部看到"我确实在跑"——
   否则失效是**静默**的（board4 那 8 h 49 min 即例证：日志落 tmpfs + 无告警 ⇒ 无人知晓）。
2. **分清实现缺陷与路线缺陷**：同一路线的不同实现，可靠性可以差很多。
   评价一条路线要拿"实现到位"的版本做基准，否则会把实现问题误判成路线问题（反之亦然）。
