# Thor04 llama.cpp 多并发 + KV 复用 实测报告

> **One-liner**: On a 14-SM DRIVE Thor board, llama.cpp multi-slot concurrency scales to ≈2.1× (4-way) / ≈2.7× (8-way) decode throughput with zero single-stream regression; prefix KV reuse saves 91-97% of prefill in multi-turn chat but is unavailable across independent requests (`llama_memory_can_shift()` = false), and the last 4 prompt tokens are always recomputed by design.


**日期**：2026-09-16
**板卡**：Thor04（板卡序列号与内网地址略），DRIVE Thor / sm_101 / 14 SM / 46 GiB
**构建**：`0.3.0-dev c589f0e`（tcgen05，与 Thor01/Thor03 同一二进制，可比）
**主模型**：Qwen3.8-27B-NVFP4-MTP-HIGH (17.0 GiB，md5 `7b563f3d…`)
**draft**：Qwen3.8-27B-DFlash2-Q2_K_S-MIX (536 MiB, md5 `a5f721e0…`)
**目的**：判断 llama.cpp 内置的多 slot 并发 + 前缀缓存能否满足需求，或是否必须上 vLLM（需从源码编译，多日工作量）

## 一、结论速览

| 问题 | 结论 |
|---|---|
| 多 slot 并发有效吗？ | **有效，但严重次线性饱和**。4 路 ≈ 2.1×，8 路 ≈ 2.7×（瞬时口径），4→8 只多 26% |
| 收益来自哪？ | **完全来自多 slot**。np=1 收 4 路并发聚合 = 29.03 t/s ≈ 单流，零提升 |
| 开多 slot 会拖慢单流吗？ | **不会**。np=4 串行逐请求复现 np=1 基线到 ±0.06 t/s |
| **np 该怎么设？** | **np ≥ 峰值并发数**（让波数 = 1）。np 不是速度旋钮；固定 2 路时 np=2/4/8 结果一致。np 开大无坏处，唯一代价是上下文被均分 |
| 为什么 np=2 与 np=3 结果相同？ | **波数 = ⌈并发数÷np⌉**。4 路时 ⌈4/2⌉=⌈4/3⌉=2 波 → 总耗时相同（69.8 vs 69.6 s）；np=4 只需 1 波 → 53.2 s |
| 多轮对话能复用 KV 吗？ | **能**。首轮前缀 594 token（= 598 − 末尾 4）恒定复用 → prefill 1717→515 ms（3.3×）。但**助手回复之后每轮重算** → 长对话 prefill 成本随轮次**线性增长** |
| 跨请求共享 system prompt 能复用吗？ | **不能**。同一长前缀+不同问题 → 只省 7%，全量重算 prefill |
| 为什么不能？ | `llama_memory_can_shift()` 在本后端返回 false → `--cache-reuse` 被运行时禁用（**与 dflash 无关**，无 draft 时同样禁用） |
| 需要 vLLM 吗？ | **并发调度不需要**（llama.cpp 已有连续批处理）；**跨请求前缀缓存是真缺口**，但只影响「固定 system prompt + 独立提问」场景 |

## 二、多并发扩展性

全部对照同 8 道题（与 Thor01/Thor03 同题库），除 `-np` 外参数完全一致（`-c 32768 -ngl 99 -fa on --temp 0` + dflash draft n=7）。

| 配置 | 端到端聚合 | 瞬时聚合¹ | 单请求均值 | 相对单流² |
|---|---|---|---|---|
| np=1 单流（前4题干净值） | 34.90 t/s | — | 34.90 | 1.00× |
| np=1 / 4 路并发（**控制组**） | 29.03 t/s | — | 31.97 | **0.83×（无提升）** |
| np=2 / 2 路并发 | 50.70 t/s | 61.28 | 30.64 | 1.45× / 1.76× |
| np=4 / 4 路并发 | 60.12 t/s | 73.95 | 18.49 | 1.72× / 2.12× |
| np=8 / 8 路并发 | 65.39 t/s | 93.14 | 11.64 | 1.87× / 2.67× |

¹ **瞬时聚合** = 各请求自身 decode 速率之和。代表「槽位持续有请求」的稳态吞吐能力（连续到达场景）。
² **端到端聚合** = 总生成 token / 墙钟。N 个请求同时发、跑完即止的批量口径，因错峰收尾的尾巴而低于瞬时值。

**扩展性曲线**：1 → 1.45 → 1.72 → 1.87（端到端）／1 → 1.76 → 2.12 → 2.67（瞬时）。
4 路到 8 路：聚合仅 +8.8%（端到端）/ +26%（瞬时），而单请求速率腰斩（18.49 → 11.64）。
→ **算力（14 SM）已是瓶颈，加 slot 只是把同一份算力切得更细**。

### ★ np 是「坑位数」不是「速度旋钮」（单变量实验）

上面各组的并发数与 np 是绑定的（2/2、4/4、8/8），无法分辨「是 np 起作用还是并发数起作用」。
故补做**固定并发数、只改 np** 的对照（同题同参）：

| 固定并发 | np=2 | np=4 | np=8 |
|---|---|---|---|
| 2 路 | 50.70 (30.64) | **48.88 (29.94)** | **50.54 (30.59)** |
| 3 路 | 50.44 (31.06) | 56.03 (23.57) | — |
| 4 路 | 45.87 (26.85) | 60.12 (18.49) | — |

（单元格 = 端到端聚合 t/s，括号 = 单请求均值 t/s）

**关键结论：只有 2 个请求时，np=2 / np=4 / np=8 结果完全一致**（50.70 / 48.88 / 50.54，差异在噪声内）。
→ **单请求速度只取决于「此刻有几个请求在争 GPU」，与 np 无关。np 开大不会拖慢单请求。**

**★ 总耗时由「波数」决定：波数 = ⌈并发数 ÷ np⌉**

| 并发数 | np | 波数 | 墙钟 | 端到端聚合 | 单请求 |
|---|---|---|---|---|---|
| 4 | 2 | **2** | 69.8 s | 45.87 | 26.85 |
| 4 | 3 | **2** | 69.6 s | 45.97 | 22.06 |
| 4 | 4 | **1** | **53.2 s** | **60.12** | 18.49 |
| 3 | 2 | **2** | 47.6 s | 50.44 | 31.06 |
| 3 | 3 | **1** | 43.4 s | 55.31 | 21.54 |

→ **np=2 与 np=3 在 4 路并发下几乎完全相同（45.87 vs 45.97），因为 ⌈4/2⌉ = ⌈4/3⌉ = 2 波。**
这是「np=3 白加了坑」的真正原因 —— 不是 np 无效，而是**波数没变**。

**选 np 的唯一标准：让波数 = 1，即 np ≥ 峰值并发数。**
- np 开小 → 第 np+1 个用户要等上一波跑完（4 路场景总时间 53 s → 70 s，慢 32%）
- np 开大 → 无坏处（不拖慢单请求），**唯一代价是上下文被均分**（`n_ctx_slot = -c / np`）
- ⚠️ **不能笼统说「np=2 是甜点」** —— 仅当峰值并发 ≤2 时成立；峰值 4 人时应用 np=4。

### 控制组的意义
`np=1` 收 4 路并发时，聚合 29.03 t/s，与单流基线 29.07 无差异 —— 请求被**串行排队**，每个请求仍拿到接近满速（req0 32.27 / req1 38.31 / req2 37.81），但第 4 个要等到 110s 才完成。
→ 证明并发收益 **100% 来自多 slot 的连续批处理**，不是「同时发请求」这个动作本身。

### 单流无退化（多 slot 无副作用）
np=4 服务上串行发 4 个请求，逐请求与 np=1 基线对比：

| 请求 | np=1 基线 | np=4 串行 | 差 |
|---|---|---|---|
| P1 | 33.58 | 33.64 | +0.06 |
| P2 | 40.73 | 40.73 | −0.00 |
| P3 | 38.15 | 38.16 | +0.01 |
| P4 | 27.15 | 27.16 | +0.01 |

→ 近乎完美复现。**开 4 个 slot 不额外消耗算力**，只在真有并发时才启用。

### ⚠ 基线口径更正
之前记录的「Thor04 基线 29.07 t/s」是 **8 题平均**，其中前 4 题均值 34.90、后 4 题均值 23.24。
逐题核对：慢的是 **P5 中文散文（16.91）与 P8 系统设计（19.42）**，而 P2 JSON 达 40.73。
np=1 与 np=8 两组的「最慢题」都是同一道 P5，比值稳定 0.36-0.50 → **是题目特性（draft 接受率差异），不是时间退化**。
→ **单流能力应记 34.90 t/s（干净口径）**，29.07 偏保守。

## 三、KV / 前缀复用

### 3.1 复用判定逻辑（读源码确认）
`tools/server/server-context.cpp`：
- L1584 `lcp_len = tokens.get_common_prefix(task.tokens)` —— 与槽内缓存求最长公共前缀
- L1585 `f_sim = lcp_len / task.tokens.size()` —— 用新 prompt 长度归一
- L1590 选 `f_sim` 最大且 > 0.1 阈值的槽
- L1191 `if (!llama_memory_can_shift(...)) { n_cache_reuse = 0; SRV_WRN("cache_reuse is not supported by this context…") }`

### 3.2 实测：三类场景

#### ⚠ 先看一个前置事实：主模型是「思维链模型」

核实响应结构（`thor04_verify_multiturn.py`）：
```
finish_reason = length
message keys  = ['role', 'content', 'reasoning_content']
content            = ''                                  ← 空
reasoning_content  = '我们需要回答用户中文请求：“请用一句话概括…'   ← 内容全在思维链
```
`max_tokens` 偏小时，token 被思维链吃光，**还没输出正式答案就被 `length` 截断，`content` 为空**。
→ 影响了后面的复用量测量（见 3.3），也意味着**「首字延迟」要分「思维链首字」和「可见答案首字」两个口径**。

#### 复用实测

| 场景 | prompt | eval token | prefill | 复用率 |
|---|---|---|---|---|
| 冷启动 | 598 | 598 | 1710.3 ms | — |
| **多轮 + 空回复**（上一版测试） | 619 | **25** | 469.5 ms | 96% |
| **多轮 + 真实回复(62字)** | 656 | **62** | 515.2 ms | **91%** ✅ |
| **多轮 + 无助手消息** | 610 | **16** | 329.0 ms | **97%** ✅ |
| 完全相同 prompt | 599 | 4 | 176.0 ms | 99% ✅ |
| 同一长前缀+不同后缀 | 599 | 557 | 1273.4 ms | **7%** ❌ |
| 完全无关内容 | 599 | 557 | 1290.8 ms | 7% ❌ |

**★ 复用边界：末尾 4 个 token 永不复用（与模板无关，已实测）**

用「同一 prompt 发两次」隔离出纯缓存行为，两种端点交叉验证：

| 端点 | 第 1 次 | 第 2 次（完全相同） | 结论 |
|---|---|---|---|
| `/v1/chat/completions`（有模板） | 598 | **4** | — |
| `/completion`（raw 文本，**无模板**） | 546 | **4** | 与模板无关 |

→ **raw 端点无模板时也是 4** → 证明这 4 个 token **不是助手角色头**（我最初的推断错误）。

严格延伸验证（raw 端点）：prompt 546 → 553（+7 token），eval = **11 = 7 + 4** ✅ 完全吻合。

**规律（实测）**：llama.cpp 每次会重算**末尾 4 个 token**，其余部分只要与前缀逐 token 相同就复用。

**机制（源码证据，非推断）** —— `tools/server/server-context.cpp` L3543-3549：
```cpp
// process the last few tokens of the prompt separately in order to allow for a checkpoint to be created.
// create checkpoints that many tokens before the end of the prompt:
//  - 4 + n_ubatch
//  - 4
// ref: https://github.com/ggml-org/llama.cpp/pull/20288
static const int checkpoint_offsets[] = {4 + n_ubatch, 4};
```
→ llama.cpp **有意**把 prompt 末尾 4 个 token 单独分批，以便在 prompt 末端附近创建 context checkpoint。
偏移量硬编码为 `{4 + n_ubatch, 4}`，与实测的「末尾 4 token 重算」吻合。
（注：这是设计使然，非缺陷；`get_common_prefix()` 本身返回完整 LCP，不含减法。）

**多轮对话的复用边界（594 token）由此解释**：
首轮 prompt 598 − 末尾 4 = **594** 复用；下一轮起，594 之后（含助手回复 + 新问题）都要重算。
- 有真实回复(62字) → eval 62（回复 46 + 新问题 + 末尾 4）
- 无助手消息 → eval 16（新问题 + 末尾 4）

→ **助手回复之后的内容每轮重算**，即使它是上一轮模型自己生成的。
原因：缓存里是**思维链 token**，下一轮渲染时思维链被剥离（只留 `content`）→ 序列在角色头处分叉。

**精确规则**：新 prompt 必须与槽内已缓存序列**逐 token 严格延伸**。
- ✅ 多轮对话：模板 + 首轮用户消息（594 token）稳定复用 → 省掉大段 prefill
- ⚠️ 助手回复之后的内容**不在复用范围**，每轮重算 → 长对话 prefill 成本**随轮次线性增长**
- ❌ 「固定 system prompt + 不同用户提问」两条独立请求：尾部不同 → 全量重算（需 KV 移位，而移位能力被禁用）


### 3.3 `--cache-reuse` 为何无效
`--cache-reuse` 的功能正是「KV 移位 + 部分复用」，但它依赖 `llama_memory_can_shift()`：

| 配置 | 是否报 not supported | eval token（599/4/557/311/516 参考） |
|---|---|---|
| dflash + `--cache-reuse 256` | 是 | 599/4/557/311/516 |
| 无 dflash + `--cache-reuse 256` | **是（同样禁用）** | 599/4/557/311/516 |

→ **根因（源码 + 对照实测）**：源码 L1191 在加载时就用 `llama_memory_can_shift()` 门控，
为 false 则把 `n_cache_reuse` 置 0 并打警告；L3213 运行时同样以 `can_cache_reuse = llama_memory_can_shift(...) && !has_mtmd` 兜底。
本后端 `can_shift = false` → **无论有没有 dflash 都被禁用**（两组配置 eval token 逐字节一致，实测确认）。

### 3.4 prefill 速率（TTFT 瓶颈）
- 冷启动 prefill：598 token / 1743 ms ≈ **343 t/s（2.9 ms/token）**
- 多轮复用后：25 token / 470 ms（其中大部分是固定开销）
- 并发下 prefill 变慢：np=4 时每请求 ~1630 ms，np=8 时 ~2976 ms（共享算力 + 排队等待）

→ 538 token 的 system prompt，每次新会话要付 ~1.6 s prefill。**这是跨请求缓存缺口的实际代价**。

#### ⚠ 并发会把 prefill 放大近 4 倍（新发现，值得警惕）

同 **np=4** 服务上，串行发请求 vs 同时发 4 路并发，prefill 延迟对比：

| 请求 | 串行 prefill | 并发 prefill | 放大 |
|---|---|---|---|
| req0 | 613 ms | 1630 ms | 2.66× |
| req1 | 340 ms | 1629 ms | 4.79× |
| req2 | 394 ms | 1627 ms | 4.13× |
| req3 | 325 ms | 1628 ms | 5.01× |
| **均值** | **418 ms** | **1629 ms** | **3.90×** |

**关键异常**：并发时 4 个请求的 prefill 都 ≈1629 ms，**与各自 prompt 长度无关**（串行时分别是 613/340/394/325）。
→ **【推断，机制未验证】** 并发下 prefill 疑似按「当前批次里有几个 prompt 在算」等长切分，
而非按 token 比例分摊算力 —— 依据是 4 个请求的 prefill 都 ≈1629 ms，**与各自 prompt 长度无关**
（串行时分别是 613/340/394/325）。已实测确认的只有「等长」这一现象，底层调度机制未经代码验证。
np=8 更极端：均值 **2978 ms**（约 8 倍串行 ~340 ms 的量级）。

**实际影响**：并发只提升了 decode 总吞吐（多 slot 交错解码有效），但**TTFT 显著恶化**。
若业务对首字延迟敏感（车载语音助手要求 <200ms，实测已远超），**并发数不能开大**，或者必须靠 KV 复用来抵消 prefill 成本。

## 四、vLLM 决策建议

**不需要为「并发调度」上 vLLM**：llama.cpp 已内置连续批处理 + 多 slot，实测 4/8 路并发可用且不拖慢单流。瓶颈在 14 SM 的算力，vLLM 无法凭空造算力。

**「跨请求前缀缓存」是真实缺口**，vLLM 的块级 prefix caching 能命中「同一 system prompt + 不同提问」的场景，而 llama.cpp 在此场景下每次全量重算。
- 若目标负载是**多轮对话**（车载助手主场景）→ llama.cpp 已是最优，无需 vLLM
- 若是**固定长 system prompt + 大量独立短请求**（RAG/批处理/多用户冷启动）→ 这是唯一值得考虑的 vLLM 理由

**代价对比**：vLLM 在 sm_101 无官方支持、无社区先例、wheel 排除 sm_110/sm_101a，需从源码编译（torch aarch64 + Triton ptxas 打补丁），多日工作量且失败风险高。

**低成本替代方案**（建议优先试）：
1. 缩短 system prompt（538 token 偏长，可压缩）
2. 会话保持（session affinity）：让每个会话固定占用一个 slot，多轮复用即生效
3. 关注 llama.cpp 上游是否支持本后端的 `can_shift`（代码已在，仅后端能力缺失）
