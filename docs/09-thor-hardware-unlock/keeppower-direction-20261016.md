# 拆车车规Thor解锁保电攻关：方法与方向概览

> 面向台架折腾拆车件的公开方向性说明。只讲机制与方向，**不含可照抄的操作步骤**
> （无具体针脚、无报文参数、无命令、无工具脚本）。机制描述基于对某一批次固件
> （11T/CSC 系列）的实测，套用到其它板/批次前请先自行实测其电源管理模型。

## 一、问题是什么

NVIDIA DRIVE Thor 车规 SoC模块从车上拆下放到台架后，
只接常电（KL30）会出现一个"上电 → 运行约 10~26 秒 → 断电睡眠"的循环，板子无法在台架
上持续保活。

**关键点**：这个"断电"的决策是由板载**电源管理控制器（MCU）**做出的，
而不是 SoC / Linux 侧自己关机。要保住电，得先理解 MCU 侧的判电逻辑。

## 二、核心机制：双闸门

台架实测表明，稳定持续保电需要**两个条件同时满足**（双闸门）：

1. **点火信号在位**（ACC / 点火线有效）
2. **车辆网络活动存在**（CAN 总线上有持续的唤醒 / 保活报文活动）

部分型号只满足其一可能不够。只给点火、没有车辆网络活动时，MCU 会记录到唤醒源，
但因车辆环境条件不满足，仍按流程断电。这是**设计行为**
（对应"车上通电但熄火驻车"的节能保护），不是故障。

> 这是整个攻关里最重要的方向性结论：**它不是"缺一个开关"，
> 而是"要同时满足两类条件"。**

## 三、四种方法（并列）

### 方法一：ACC 法（点火接线法）

- **方向**：给电源管理控制器一个物理点火信号。
- **原理**：MCU 判定"点火中"时，休眠定时器不激活。
- **要点**：需要定位板上真正的点火检测引脚（要拿万用表 + 限流电阻逐针探测，
  误接可能伤板）；且**点火闸门打开后，部分型号车辆网络那一闸门仍然可能需要满足**。
- **性质**：可落地的硬件方向，但部分型号单靠它保不住电。

### 方法二：CAN 报文法

- **方向**：在 CAN 总线上注入网络管理（Network Management）报文，
  满足唤醒 / 保活条件。
- **原理**：MCU 在监听车辆网络，检测到有效的网络管理活动，
  就把板子当作"处在活的车里"。
- **要点**：
  - 该类板的 CAN 通道是 **CAN-FD**，经典 CAN 卡喂不了，得用支持 FD 的适配卡；
  - **报文注入的时机很关键**——收发器只在板上电窗口内有电，睡眠态灌帧是空转；
  - **"能唤醒 ≠ 能保电"**：注入报文能把板子从睡眠态叫醒，但持续保电
    还需要满足保活条件，且要喂对正确的总线。
- **现状（公开口径）**：唤醒链路已验证可行；已经有稳定保电所需的准确报文与总线。

### 方法三：看门人静默法

- **方向**：给MCU按一定规则发出特殊指令，让电源管理控制器保持静默，从而让 SoC 长时间运行。
- **性质**：电源管理控制器静默后，相关电源管理都静默，只能台架用，绝不能上车。
- **原理**：断电动作由 MCU 发起；MCU 一静默，就没有人再给 SoC 发断电指令。
- **要点**：指令发出时机有限制；
  MCU静默，退出路径只有物理断电，断电前Linux侧干净关机(shutdown)。
- **现状**：已经多次完整复现。

### 方法四：定制固件法

- **方向**：修改电源管理控制器的固件，从根源改掉电源管理 / 休眠逻辑。
- **性质**：**最彻底**的方案。断电判电逻辑直接在固件里改掉，
  不再受"双闸门"约束，也不再依赖外部接线或灌帧。
- **要点**：需要深度的嵌入式固件工程能力（固件逆向 / 修改 / 重写 / 重刷），
  门槛高、周期长。需要有相关SDK和NGC开发账号。
  **本方在实操中，这一部分交由外部专业固件工程团队完成，
  不自行实施。**
- **现状（公开口径）**：方向上最确定，进行中。

## 四、整体判断

- **方法一、二**：都落在"双闸门"上，需**并行**解决，单靠任一都不够。
- **方法三**：是台架实验的窗口工具，不是最终解。
- **方法四**：最彻底，但依赖外部固件工程能力。
- **可组合**：先用方法三开诊断窗口、在 SoC 侧取证，
  再用方法一 / 二做实车条件验证，最后由方法四收口。
