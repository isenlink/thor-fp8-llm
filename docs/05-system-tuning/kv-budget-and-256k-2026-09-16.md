# KV cache budget and 256K feasibility on DRIVE Thor (measured ladder)

**English summary**: Because only 16 of the model's 65 layers are full-attention (the rest are linear-attention / GDN), KV costs just 64 KB per token in f16 — so a full 256K context needs only ~17 GB and fits the 58 GiB unified memory. We ran the full ladder (30K → 254K input, 1024-token outputs): decode degrades gently (−28%), the real cost is prefill time (67 s → 25.6 min), and prefix caching makes follow-up questions on the same long document nearly free (TTFT 25.6 min → 5.9 s).

# KV 预算与 256K 长上下文实测（2026-09-16）

> 平台：DRIVE Thor（p3960-0010 / T264 / sm_101a / DriveOS 7.0.3，统一内存 58 GiB，46 GiB 大页池）
> 模型：Qwen3.8-27B NVFP4（17.6 GB）+ DFlash2 草稿（0.56 GB）；KV **f16**

---

## 1. KV 几何：先看模型结构，别按"层数 × 头数"瞎估

从 GGUF 元数据直接读（`qwen35` 架构）：

| 项 | 值 |
|---|---|
| 层数 | **65** |
| **全注意力层** | `full_attention_interval = 4` ⇒ **只有 16 层是全注意力**（其余 49 层是线性注意力 / GDN，状态恒定不随 ctx 增长） |
| KV 头 / 头维 | `head_count_kv = 4`，`key_length = value_length = 256` |
| 模型原生上限 | `context_length = 262144`（256K） |
| **KV 每 token** | 2(K+V) × 4 头 × 256 dim × 2 B × 16 层 = **64 KB/token（f16）**；q8_0 ≈ 33 KB/token |

⇒ **混合线性注意力带来一个巨大的隐藏红利**：KV 只按 16 层线性增长，不是 65 层。
按 65 层误估会把 KV 算大 4 倍，从而做出"256K 装不下"的错误结论。

## 2. 内存账（58 GiB 统一内存 + 46 GiB 大页池）

| ctx 上限 | f16 KV | 权重(17.6) + 草稿(0.56) + KV | 余量 | 判定 |
|---|---:|---:|---:|---|
| 32K | 2.1 GB | 20.3 GB | 37 GB | ✅ |
| 64K | 4.2 GB | 22.4 GB | 35 GB | ✅ |
| 128K | 8.4 GB | 26.6 GB | 31 GB | ✅ |
| **256K** | **16.8 GB** | **35.0 GB** | ~23 GB | ✅ **实测跑通** |

**实测校验**：256K 跑起来时观测大页池占用峰值 ≈ **34.7 GB**，与预算 35.0 GB 吻合（误差 <1%）。
⇒ **"ctx 上限设大"本身不花速度**——解码只取决于**实际** KV 长度；上限只是容量预留。
**建议直接用原生上限 262144**，不要为省内存把 KV 卡小。

## 3. 实测阶梯（长文输入 + 1024 token 长输出，同配置同提示词风格）

| 输入 token | ctx 上限 | 预填充 t/s | **TTFT** | **解码 t/s** | acceptance | 该档墙钟 |
|---:|---:|---:|---:|---:|---:|---:|
| 29,918 | 32768 | 448.8 | **66.8 s** | **17.90** | 0.246 | 124 s |
| 61,935 | 65536 | 361.2 | **171.6 s** | **16.79** | 0.250 | 233 s |
| 125,504 | 131072 | 256.9 | **488.8 s** | **15.05** | 0.258 | 557 s |
| **253,514** | **262144** | 163.3 | **1552.7 s（25.9 min）** | **12.92** | 0.288 | 1632 s |

**三条读法**：
1. **解码随上下文衰减温和**：30K → 256K 只掉 **−28%**（17.90 → 12.92）——
   因为只有 16/65 层全注意力，KV 遍历不是主导开销；
2. **代价全在预填充**：448.8 → 163.3 t/s（**−64%**），TTFT 近似线性增长（≈6 s/千 token @256K）；
3. **长逻辑内容本身难预测**：acceptance 只有 0.25-0.29（摘要类约 0.40），所以"长文输入 + 长分析输出"
   的解码只有 13-18 t/s——**这是内容属性，不是配置问题**。

## 4. ⭐ 关键用法：一次载入、反复提问（让 256K 真正可用）

复测时做了两次请求（同 ctx 262144、同 25 万 token 长文）：

| 请求 | 预填充 token | **TTFT** | 解码 t/s | 总墙钟 |
|---|---:|---:|---:|---:|
| ① 首次（冷） | 252,532 | **1536.3 s（25.6 min）** | 14.03 | **1609.6 s** |
| ② 同一长文 + **换问题** | **520** | **5.9 s** | **17.78** | **63.9 s** |

**第二个问题的预填充只有 520 个 token**（不是 25 万）——前缀缓存命中，**TTFT 从 25.6 分钟降到 5.9 秒，
总耗时差 25 倍**。

⇒ **长上下文的正确产品姿态**：
- ✅ **一次喂入长文档 → 反复追问**（预填充只付一次）；
- ❌ 每次换一份新长文档问一句（每次都要重付 26 分钟）。

## 5. 按场景的档位建议

| 场景 | 输入规模 | 建议 ctx 上限 | 实测 TTFT | 实测解码 |
|---|---|---:|---:|---:|
| 文案 / 日常问答 | < 8K | 32768 | < 20 s | ~20 t/s |
| **长文档分析 / 纪要（推荐主力）** | 30-60K | **65536** | **1-3 min** | 16-18 t/s |
| 长报告 / 代码库 | 100-128K | 131072 | 8 min | 15 t/s |
| 超长文档（全书级） | 250K+ | **262144** | 26 min（**仅首次**） | 12.9-17.8 t/s |

**KV 类型保持 f16**：本平台长档实测 f16 优于 q8_0（q8_0 省一半内存但反量化开销 + 草稿质量双重惩罚）。
若确实要腾内存给别的用途，再考虑 q8_0，并**必须重新实测 acceptance**。

**稳定性观测（256K 全程 84 个采样点）**：`MemAvailable` 稳定在 5.8-7.0 GB（大页池刚性占走其余），
**温度峰值 66.2°C**（设计上限约 102°C），无 OOM、无 CUDA 错误。

## 6. 复现要点

```bash
# 1) 起服务：ctx 直接给原生上限
llama-server -m <target>.gguf -md <dflash2-draft>.gguf \
  --spec-type draft-dflash --spec-draft-n-max 5 \
  -ngl 99 -c 262144 -fa on -ctk f16 -ctv f16 -np 1 --parallel 1 --temp 0

# 2) 构造长 prompt：用 /tokenize 精确计数，不要按字符密度估算
#    POST /tokenize {"content": text} -> {"tokens":[...]}
#    目标 253K 时，先 units=目标/60 起步，按实测 token 数比例修正，1-2 轮即命中

# 3) 二次提问务必复用同一长文前缀（前缀缓存生效的标志：第 2 次的 prompt eval 只有几百 token）
```

⚠️ **判据（必须查）**：日志里 `prompt eval time = … N tokens` —— **N 没上去 = 根本没测成长上下文**。
只把 `-c` 从 8192 改成 32768 而用短提示词，跑出来的数字会与 8K 档**逐位相同**（我们踩过，见
`06-benchmarks/benchmark-methodology-2026-09-16.md` §2）。
