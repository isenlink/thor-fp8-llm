## 三、三个关键发现

### 发现 1：NVFP4 必须配 tcgen05 加速，体积小 ≠ 速度快

| 模型 | 体积 | 基线吞吐 |
|---|---|---|
| **Unsloth-NVFP4-Q8** | 21.57 GiB | **11.38 t/s** ✅ |
| Qwen3.8-27B-MTP-Q4_K_M | **15.65 GiB**（小 27%） | 9.56 t/s ❌ |

**体积小 27%，速度反而慢 16%。**

**原因**：NVFP4 是 Tegra264 Tensor Core 的**原生格式**，tcgen05 内核可直接消费 fp4 数据；
传统 K-quant（Q4_K_M）需**先反量化为 fp16** 才能进 Tensor Core，多出一道开销，
抵消了体积优势。

**推论**：协作方脚本选择 NVFP4 模型 + tcgen05 构建是**配套设计**，不可拆开单独使用。

### 发现 2：DFlash2 显著优于 MTP

| Draft 方案 | 代码吞吐 | 相对基线 |
|---|---|---|
| MTP（内置 nextn head） | 19-21 t/s | +71% |
| **DFlash2** | **24-30 t/s** | **+149%** |

**MTP 无法达成"30+"**；资料所述的 30+ 实际来自 DFlash2。

### 发现 3：草稿深度必须按场景调优（完全复现资料结论）

| 深度 | 适用场景 | 实测效果 |
|---|---|---|
| **3** | 中文 / 散文 | 中文 +2.9 t/s |
| **5** | 折中（上游默认） | 均衡 |
| **7** | **代码 / JSON** | 代码 +4.0 t/s |

**中文散文是 DFlash2 的固有短板**：深度 7 时仅 8.5 t/s（比基线 11.38 还慢），
深度 3 时回升到 11.3 t/s。原因见资料原文——散文接受率仅 0.12-0.16，
投机解码"猜不中"导致纯开销。**中文场景建议 n=3。**

## 六、操作注意事项（踩坑记录）

### 1. 板端服务重启的进程清理

`pkill -f 'llama-server'` **会匹配到 SSH 自身命令行**，导致连接自杀（exit 255）。
`fuser 8080/tcp` 返回的 PID 也不可靠。

**可靠做法：**
```bash
PID=$(ss -tlnp | grep ':8080' | grep -oE 'pid=[0-9]+' | head -1 | cut -d= -f2)
kill $PID; sleep 12; kill -9 $PID 2>/dev/null
pgrep -x llama-server | while read p; do kill -9 $p 2>/dev/null; done   # 兜底
```

**残留进程会占着 8080 导致新实例 `couldn't bind`，且占用 GPU 内存。**

### 2. llama-cli 不适合做基准

`llama-cli` 生成完指定 token 后会进入**交互对话模式等待 stdin**，
在 SSH 管道场景下会永久挂起。**基准测试请用 llama-server + curl**。

### 3. DFlash2 的 block_size 限制

draft GGUF 内置 `dflash.block_size=8`，llama.cpp 将 `n_draft_max` 钳制到
`block_size-1 = 7`。**设置 >7 会被静默截断**（日志会提示 note）。

### 4. 主模型与 draft 的匹配性

**DFlash2 drafter 依赖读取目标模型的 hidden states**，因此
**必须与目标模型同源**。实测将 DFlash2 drafter 用于微调版 `MTP-Q4_K_M`
主模型时，吞吐从 28.8 崩到 8.5 t/s（hidden states 语义不匹配，猜测全错）。

### 5. ★ 换模型前必须彻底清理（否则性能失真）

**症状**：残留的 `llama-server` 占着 8080 端口和 GPU 大页，
新实例会 `couldn't bind HTTP server socket` 或跑出异常慢的数字。

**已固化为脚本**：`/brand_data/llama-bin/thor03_cleanup.sh`（主机侧副本为内部产物，未入仓）

```bash
# 查看状态
bash thor03_cleanup.sh status
#   ─── 状态 ───
#     llama 进程: 1
#     8080 监听: 占用
#     HugePages_Free:    13289
#     CUDA: cuInit rc = 0
#     内存: used 56Gi / avail 1.9Gi

# 彻底清理（换模型前必跑）
bash thor03_cleanup.sh cleanup
#   ─── 清理 ───
#     1. 端口 8080 占用者 PID=44269，发送 TERM
#     2. 无 llama-server 残留
#     4. 等待大页归还...
#        ✅ 大页已全归还 (23552/23552) — 用时 1s
#   ─── 状态 ───
#     llama 进程: 0
#     8080 监听: 空闲
#     HugePages_Free: 23552        ← 全归还
#     内存: used 51Gi / avail 7.4Gi ← 从 1.9Gi 恢复
```

**清理成功判据（三条全中才算干净）**：
1. `pgrep -xc llama-server` = 0
2. `ss -tlnp | grep :8080` 无输出
3. `HugePages_Free` == `HugePages_Total`（23552/23552）

**脚本内置的防坑设计**：
- 用 `ss -tlnp` 解析真实 PID（`fuser` 返回的 PID 不可靠）
- 兜底用 `pgrep -x llama-server`（**绝不用 `pkill -f`**，会匹配 SSH 自身命令行导致 exit 255）
- 一并清理 `llama-bench` / `llama-perplexity` / `llama-cli` 残留
- 轮询等待大页归还（最多 30s），不靠固定 sleep 猜

## 八、第三轮：换模型文件（2026-09-16 凌晨）

### 8.1 下载来源分析

资料中的两个关键模型文件（HauhauCS-NVFP4-mixed + DFlash2-Q2_K_S）**均不在本机模型库**，经搜索确认来源：

| 目标 | 来源 | 说明 |
|---|---|---|
| DFlash2-Q2_K_S-MIX | `hf-mirror.com/HermiHg/Qwen3.8-27B-DFlash2-Q2_K_S-MIX-GGUF`（536 MB） | 从 incoai 原仓库复制 + Q2_K_S 量化 |
| ~~HauhauCS NVFP4-mixed~~ | `ollama.com/aiconjured/...`（17.10 GB） | **放弃**，见下 |
| **NVFP4-MTP-HIGH**（改用） | `hf-mirror.com/esatapedico/Qwen3.8-27B-NVFP4-MTP-GGUF`（17.57 GB） | **最终选用** |

**网络实测**：`huggingface.co` 直连不通（HTTP 000），`hf-mirror.com` 通（200）。
**Ollama registry 可达但仅 2.3 MB/s**；HF 镜像 10.4 MB/s（快 4.5 倍）。

**放弃 HauhauCS 的两个理由**：
1. 下载太慢（2.3 MB/s，17 GB 需约 2 小时）
2. **更关键**：它是 uncensored **微调版**，而 DFlash2 drafter 从**原版** Qwen3.8-27B 提取，
   跨模型使用会因 hidden states 语义不匹配导致崩溃（本轮已实证：微调版主模型 + DFlash2 → 8.5 t/s）

**改用 `esatapedico/Qwen3.8-27B-NVFP4-MTP-GGUF` 的优势**：
- 基座为 `unsloth/Qwen3.8-27B-NVFP4`（**原版**，与 drafter 同源）
- 448 张量全 **NVFP4** backbone（13.69 GB），契合 tcgen05 加速
- **内置 MTP 头**，同时也可外挂 DFlash2（两条路线均可测）
- 262,144 原生上下文，原生 VLM
- 九档可选，HIGH = 17.57 GB（对应资料所述 17.5 GiB）

#### 关键结论

1. **内置 MTP 不如外挂 DFlash2**（22.12 vs 39.19）——尽管该模型的 MTP 头是内置的，

2. **体积 -24% 换来 +21% 吞吐**（30.50 → 36.96 @ n=6）
3. **attention 层从 Q8_0 变 NVFP4** 后 tcgen05 覆盖更全，是加速的重要来源
4. **深度 7 优于 6**（+2.23），与资料"代码用深度 7"一致
5. **输出质量抽查正常**——代码/JSON/数学三类输出均正确，
   未见作者所警示的"attention 二次量化"带来的明显劣化

#### ⚠️ 定量质量验证（本轮补齐 — 重要）

作者明说 compact 档 attention 经 **F8 → BF16 → NVFP4 二次量化**，会有精度损失。
本轮用 `llama-perplexity` 做了**定量验证**，结果**证实了该警示**。

**两种语料交叉验证（同一 PG19 风格英文文本，n_ctx=2048）：**

| 语料类型 | 新 HIGH (16.36G) | 旧 Unsloth-NVFP4-Q8 (21.57G) | 差距 |
|---|---|---|---|
| 重复文本（39.6 KB） | PPL **2.6944** ±0.164 | PPL **2.1615** ±0.113 | 新差 24.7% |
| **非重复文本**（24.8 KB） | PPL **3.5176** ±0.313 | PPL **3.0412** ±0.250 | 新差 **15.7%** |

两种语料结论一致：**新模型 HIGH 困惑度显著更高（质量略降）**。

**★ 明确的 速度 ↔ 质量 权衡：**

| 维度 | 新 HIGH (16.36 GiB) | 旧 Q8 (21.57 GiB) | 变化 |
|---|---|---|---|
| **生成速度** | **39.19 t/s** | 30.50 t/s | **+28.5%** ✅ |
| **困惑度**（越低越好） | 3.5176 | **3.0412** | **+15.7%（变差）** ⚠️ |
| **磁盘体积** | 16.36 GiB | 21.57 GiB | -24% ✅ |

**这一权衡的根源**：compact 档把 attention 从 BF16（源为 F8）二次量化为 NVFP4，
换来全 backbone 的 tcgen05 加速，但损失了注意力精度。

**选型建议：**
- 追求**吞吐优先**（批量推理、代码补全、agent 循环）→ 用 HIGH（39.19 t/s）

## 九、长上下文测试（第四轮）

### 9.1 Prompt Processing 长度扫描（llama-bench，新模型 HIGH）

| 上下文长度 | pp 吞吐 | 相对 512 |
|---|---|---|
| 512 | **616.33** ±12.73 | 100% |
| 2048 | **624.00** ±0.10 | 101% |
| 4096 | 617.18 ±0.01 | 100% |
| 8192 | 599.22 ±0.03 | 97% |
| 16384 | 545.97 ±0.08 | 89% |
| **32768** | **469.54** ±0.04 | **76%** |

tg128（基线生成，无投机）= **13.06 t/s**

**分析**：
- 预填充最高 **624 t/s**，32K 时仍有 469 t/s（衰减 24%，属正常范围）
- 衰减平缓 → **attention 的 NVFP4 量化未破坏长上下文性能**
- 对比旧 35B Q4_K_M（pp512 739.98 / pp8192 713.67 / pp16384 694.72）：
  27B 的 pp 略低，说明 pp 阶段 NVFP4 解包有计算开销（pp 属计算密集，量化格式影响大）

### 9.2 真实长上下文场景（32K ctx + DFlash2-Q2_K_S n=7）

**配置**：`-c 32768`，启动 18 秒，`n_ctx_slot=32768`，稳定无崩溃 ✅

| 场景 | prompt tok | 生成 tok | 墙钟 | 含预填吞吐 | 纯预填充 |
|---|---|---|---|---|---|
| 长ctx + 摘要 | 3787 | 73 | 9.51s | 7.68 t/s | 398.17 t/s |
| **长ctx + 代码** | 2283 | 300 | 14.05s | **21.35 t/s** | 162.49 t/s |
| 长ctx + 散文 | 2276 | 300 | 16.85s | 17.80 t/s | 135.06 t/s |

（注：墙钟含预填充时间，"含预填吞吐"随 prompt 增长而降低；纯生成速度见第 8 章短请求测试）

### 9.3 长上下文关键结论

**1. 结构化输出仍是投机解码的最佳场景**（一致规律）
- 长ctx 下：代码 21.35 > 散文 17.80
- 短请求下：代码/JSON 39.19 >> 中文散文 8.46

**2. 长上下文首 token 延迟显著**
- 3787 token 预填约 9.5s（占总墙钟绝大部分）
- 预填充延迟随上下文线性增长

**3. 32K 上下文生产可用** ✅
- 启动 18 秒、无 OOM、无崩溃、GPU 温度 60-62°C（远低于 95°C 告警线）
- 模型原生支持 262144，本轮仅验证到 32K

**4. 用途建议**
- 长文档分析 + 代码生成 → 收益明显（21.35 t/s）
- 长文档摘要/自由写作 → 收益有限（7.68-17.80 t/s），**可考虑关闭投机解码**
