# 负结果黑名单（我们实测否决过的方向，省你重复）

判据一律是**同 boot 配对臂**、看 ms/步；所有条目都是实测，不是推测。

| 假设 | 实测 | 结论 |
|---|---|---|
| 权重拷贝粒度 4 B → 16 B | 原型 257.69 → 226.85 GB/s（只值 −12%），而缺口是 1.89× | 排除：粒度解释不了腿的慢 |
| 原型慢是因为喂的是理想化取数 | 真实 GGML 权重切片（生产寻址）227.75 → 215.28 GB/s（−5.5%） | 排除：内存侧三假设（粒度/寻址/prefetch·padding）全关 |
| MMQ prefetch / M-padding | 逐项为负 | 否决 |
| 环等待组深度 `<1>` → `<0>` | ratio 1.032，两臂 D dump 逐字节相同 | 否决 |
| A 段常驻 smem（ARES） | 102.1 vs 基线 100.9 GB/s（+1.2%） | 关闭（低于预注册门 `<110 关线`） |
| KV 量化 q8_0 @256K | 省约 6.5 GiB，decode 掉 1/3 | 不划算 |
| 「接受率拉满就能过 30 t/s」 | 满接受上界仍 <30 t/s | 否决（接受率不是唯一瓶颈） |
| 「把权重拷贝腿优化回 260 GB/s」 | 腿 136.5 GB/s vs 隔离原型 257 GB/s 差 1.88×，但粒度只值 −12%、生产寻址只值 −5.5% | **这条线已收摊**：缺口在消费者/结构侧，不在访存侧 |

## 另一类负结果：配置级

- **在线加大页池**：碎片化，实测加到约 32 GiB 就上不去了 ⇒ 必须冷启动。
- **KV q8_0 换更长上下文**：省下的内存买不到净收益，长上下文真正的成本在权重侧 + 起草器接受率。
- **多并行 `--parallel`**：单流速率下降，池被瓜分。
- **拿 t/s 比不同臂**：见 `prod-measurements.md` 的口径纪律；这条本身就是一个"负结果"（会得出假收益）。
